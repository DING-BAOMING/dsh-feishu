### P0-1：appSecret 作为工具入参 → 明文泄露在工具日志

**来源**：安全审查 S1（最高优先级）

**问题**：`feishu_verify_connection(appId, appSecret)` 把 appSecret 作为工具参数。DSH 工具执行日志会记录完整入参，`role('secret')` 只保护配置序列化，不保护工具入参日志。

```typescript
// 当前设计（有漏洞）
execute: async ({ appId, appSecret }) => {  // ← appSecret 在日志中明文
  const token = await getToken(appId, appSecret)
}
```

**修复方案**：

```typescript
// 工具入参只传 appId
feishu_verify_connection: {
  name: 'feishu_verify_connection',
  parameters: Schema.object({
    appId: Schema.string(),  // ← 不传 appSecret
  }),
  execute: async ({ appId }, ctx) => {
    // appSecret 从 credentials 运行时读取，永不进入日志
    const appSecret = await ctx.credentials.get('dsh-feishu.appSecret')
    if (!appSecret) throw new Error('请先在设置页填写 App Secret')
    const token = await getToken(appId, appSecret)
    // ...
  }
}
```

### P0-2：Client 单例 × 多 Profile 串号

**来源**：架构审查 #1 + 数据流审查 P0

**问题**：全局 `_client` 单例。DSH 支持多 Profile，Profile A 和 Profile B 各配不同飞书账号，但共用同一个 client 实例——账号 token 互相覆盖。

```typescript
// 当前设计（有缺陷）
let _client: Client | null = null
export function getFeishuClient(config: FeishuConfig): Client {
  if (!_client) { _client = new Client({ appId: config.appId, ... }) }
  return _client  // Profile B 获取到 Profile A 的 token
}
```

**修复方案**：

```typescript
// 按 profile 隔离 client 实例
const _clients = new Map<string, Client>()

export function getFeishuClient(ctx: Context, config: FeishuConfig): Client {
  const key = ctx.profile.id  // 每个 profile 独立
  if (!_clients.has(key)) {
    _clients.set(key, new Client({
      appId: config.appId,
      appSecret: config.appSecret,
      loggerLevel: LoggerLevel.error,
    }))
  }
  return _clients.get(key)!
}

export function resetClientForProfile(profileId: string) {
  _clients.delete(profileId)
}
```

同时 `onChange` 中调用 `resetClientForProfile(ctx.profile.id)`。

### P0-4：App Secret 变更后 host tools 继续用旧配置（闭包捕获）

**来源**：数据流审查 P1 + 架构审查 #2

**问题**：host tools 的 `execute` 函数在注册时闭包捕获了当时的 `config` 对象。凭证变更后，`onChange` 虽然可以 reset client，但 tools 已经 capture 了旧值。

```typescript
// 当前设计（有缺陷）
export function apply(ctx: Context, config: Config) {
  ctx.tools.register({
    name: 'feishu_upload_file',
    execute: async (params) => {
      // 这里的 config 是 apply() 时的快照
      // 用户改了 App Secret 后，这里仍然是旧值
    }
  }, { namespace: 'feishu' })
}
```

**修复方案**：tools 的 execute 中永远从 `ctx.credentials` 动态读取，不 capture：

```typescript
execute: async (params, ctx) => {
  const appSecret = await ctx.credentials.get('dsh-feishu.appSecret')
  const config = await ctx.settings.get('dsh-feishu')  // 最新配置
  const client = getFeishuClient(ctx, config)
  // ... 使用 client 而不是直接用 config 里的凭证
}
```

### P0-5：localPath / savePath 无路径限制 → 任意文件读写

**来源**：安全审查 S2/S3（极高风险）

**问题**：
- `feishu_upload_file` 的 `localPath` 可指向任意系统文件（如 `/etc/passwd`）
- `feishu_download_file` 的 `savePath` 可覆盖任意文件（如 `C:\Windows\System32\config.sys`）

**修复方案**：

```typescript
// 白名单路径验证
const ALLOWED_PATHS = [
  process.env.DSH_HOME!,   // ~/.dsh/
  process.env.DSH_DATA!,   // DSH 数据目录
]

function validatePath(path: string): boolean {
  const resolved = path.resolve(path)
  return ALLOWED_PATHS.some(p => resolved.startsWith(resolve(p)))
}

execute: async ({ localPath }) => {
  if (!validatePath(localPath)) {
    throw new FeishuError('路径不在允许范围内', 'PATH_FORBIDDEN')
  }
  // ...
}
```

### P0-6：QPS 5 限流完全无实现

**来源**：安全审查 M3 + 我自己的分析

**问题**：规格写了"队列+延迟"，代码是空的。Agent 并发调用 6 个工具会直接触发飞书 230001 限流错误。

**修复方案**（Phase 1 必须实现）：

```typescript
// src/lib/rateLimit.ts
class RateLimiter {
  private tokens = 5
  private lastRefill = Date.now()
  private queue: Array<() => void> = []

  async acquire(): Promise<void> {
    this.refill()
    if (this.tokens > 0) {
      this.tokens--
      return
    }
    return new Promise(resolve => {
      this.queue.push(resolve)
      setTimeout(() => {
        this.refill()
        if (this.tokens > 0) {
          this.tokens--
          const next = this.queue.shift()
          if (next) next()
        }
      }, 200)  // 每 200ms 补充 1 个令牌
    })
  }

  private refill() {
    const now = Date.now()
    const elapsed = now - this.lastRefill
    const refillCount = Math.floor(elapsed / 200)
    this.tokens = Math.min(5, this.tokens + refillCount)
    this.lastRefill = now
  }
}

export const rateLimiter = new RateLimiter()
```

## 🟡 P1 重要问题（Phase 1 中修复）

### P1-1：>20MB 文件需分卷方案（不仅是错误提示）

**来源**：数据流审查 P0 + 我的分析

**当前设计**：超限直接返回错误，引导用 dsh-config-manager 压缩。

**问题**：用户备份 DSH 配置可能产生 >20MB 文件（大量 skills / 本地插件）。直接拒接体验差，且 dsh-config-manager 压缩后仍然是 >20MB 单文件（ZIP 不支持分卷）。

**修复方案**：v1 分两个阶段：

```
v1.0：超限拒接 + 引导手动压缩（体验差但安全）
v1.1：实现飞书 multipart upload（分块上传）
  Step 1: POST /upload_multipart/init → session_id
  Step 2: 每块 ≤ 18MB → POST /upload_multipart/{session_id}
  Step 3: POST /upload_multipart/{session_id}/finish → 合并
  Step 4: 出错 → POST /upload_multipart/{session_id}/abort → 清理
```

规格中增加 `feishu_upload_chunked` 的接口设计定义（即使 v1.1 才实现）。

## 📋 GitHub PR 安全审核配置（AI 时代）

### 推荐配置（owner = 人类，你）

```yaml
# .github/CODEOWNERS
* @your-github-username
src/** @your-github-username
/tests/** @your-github-username
*.md @your-github-username
```

**Branch Protection Rules**：
- ✅ Require pull request before merging
- ✅ Require at least 1 approving review（必须是 CODEOWNER）
- ✅ Require status checks to pass (pnpm build + pnpm test + pnpm lint)
- ✅ Do not allow bypassing

**不要启用**：完全自动合并（auto-merge）。如果需要，用 `/auto-merge` 手动触发。

**效果**：即使 AI（我）写的代码，CI 全绿，也必须你亲自点 Approve 才能合并。你永远不需要"看懂"PR——只需：
1. 看 diff 改了哪几个文件
2. CI 是否全绿
3. 问 AI 这改了什么的简述
4. 点 Approve 或要求修改
