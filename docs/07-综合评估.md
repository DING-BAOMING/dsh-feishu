## 一、GitHub 自动化合并：最终结论

### 问：能不能我和你都不参与，AI 自动定时合并？

**结论：不可以。技术上可行，安全上不可接受。**

| 方案 | 参与度 | 风险 | 适用场景 |
|------|--------|------|---------|
| CI 全绿即自动合并 | 零 | 🔴 恶意代码直接进主线 | 内部测试项目 |
| Mergify + owner PR | 你（点合并） | 🟡 你的 PR 才自动合 | 你自己维护的项目 |
| 找共同审核者 | 你朋友（点审核） | ✅ 安全 | 有信任的共同维护者 |
| 手动 Merge（推荐）| 你（点 Merge） | ✅ 安全 | **你当前最佳选择** |

**推荐操作（最小参与）**：
1. CI 全绿 → 你点 Merge（2 秒）
2. 你永远不读代码，只看 CI 颜色
3. 我帮你写代码 + CI 配置

## 三、API 分卷/分块方案（>20MB）

### 飞书云盘分块上传接口

飞书提供 `multipart upload` 接口族：

```
POST   /upload_multipart/init          → 初始化，返回 session_id
POST   /upload_multipart/{session_id}  → 上传每块（二进制）
POST   /upload_multipart/{session_id}/finish  → 完成合并
POST   /upload_multipart/{session_id}/abort    → 取消清理
```

### 分块策略（v1.1 实现）

```typescript
interface ChunkedUploadSession {
  sessionId: string
  fileName: string
  totalSize: number
  chunkSize: number        // 默认 18MB（留 2MB 余量）
  uploadedCount: number
  fileTokens: string[]     // 每块上传后的 token
}

async function uploadChunked(
  localPath: string,
  folderToken: string,
  onProgress?: (pct: number) => void
): Promise<string> {
  const fileSize = fs.statSync(localPath).size
  const chunkSize = 18 * 1024 * 1024  // 18MB
  const chunks = Math.ceil(fileSize / chunkSize)

  // Step 1: init
  const { sessionId } = await api.post('/upload_multipart/init', {
    file_name: path.basename(localPath),
    parent_type: 'explorer',
    parent_node: folderToken || '',
    size: fileSize,
  })

  // Step 2: upload each chunk
  const fileTokens: string[] = []
  for (let i = 0; i < chunks; i++) {
    const buffer = fs.readFileChunk(localPath, i * chunkSize, chunkSize)
    const result = await api.post(`/upload_multipart/${sessionId}`, buffer, {
      headers: { 'Content-Type': 'application/octet-stream' }
    })
    fileTokens.push(result.file_token)
    onProgress?.(Math.round((i + 1) / chunks * 100))
  }

  // Step 3: finish
  const { file_token } = await api.post(`/upload_multipart/${sessionId}/finish`, {
    file_tokens: fileTokens,
  })
  return file_token
}
```

## 四、架构耦合分析

### 当前内聚/耦合评估

| 模块 | 内聚 | 耦合 | 评价 |
|------|------|------|------|
| `lib/client.ts` | 🟡 中 | — | 单例管理合理，但需支持多 Profile |
| `lib/drive.ts` | 🟢 高 | 低 | 一个文件封装一个模块 |
| `lib/docx.ts` | 🟢 高 | 低 | 同上 |
| `lib/bitable.ts` | 🟢 高 | 低 | 同上 |
| `lib/errors.ts` | 🟢 高 | 无 | 纯工具类，高内聚 |
| `lib/rateLimit.ts` | 🟢 高 | 无 | 独立工具类 |
| `tools/drive.ts` | 🟢 高 | 通过 `client.ts` | 与具体 API 封装解耦 |
| `client/FeishuCard.tsx` | 🟡 中 | 依赖 4 个 tab 组件 | 可接受，UI 组件自然有依赖 |

**总体评估**：架构内聚性良好，模块间通过 `client.ts` 单一入口耦合，接近低耦合标准。

### 改进建议

1. `lib/drive.ts`、`lib/docx.ts`、`lib/bitable.ts` 可合并为 `lib/services.ts`（3 个文件功能相似，扁平结构更清晰）
2. `lib/auth.ts` 删除（已识别为冗余）
3. `src/client/tabs/` 拆分为独立包 `src/client/features/`（drive/docx/bitable 三模块隔离）
